# Command Center: endpoints (`/operator/v1`)

Every operator-API endpoint. The router is `server/src/operator/routes.ts` (with `tenants.ts`, `plans.ts`, `onboarding.ts`, `overrides.ts`, `overview.ts`, `health.ts`, `security.ts`, `sessions.ts`, `audit.ts`, `announcement.ts`, `inviteAccept.ts`), mounted at `/operator/v1` in `server/src/app.ts`. This file changes in the same commit as any operator route.

Every route goes through, in order:
1. Correlation id: echoes `X-Correlation-Id` if it matches `^[\w.-]{1,100}$`, else generates a UUID; set on the response.
2. `requireOperator`: IP allow-list (`OPERATOR_IP_ALLOWLIST`), Bearer token verified locally against the operator realm keys (issuer `${ID_ISSUER_ORIGIN}/realms/operator`, audience `urn:karbexa:operator`, RS256, `typ: at+jwt`, `token_use: 'access'`), then the account must still be active with an operator role and a live `OperatorSession`. Each route then passes `requirePermission('<perm>')` (403 `FORBIDDEN` without it; permissions in `ACCESS.md`). Failures: 403 `FORBIDDEN` (IP), 401 `NO_TOKEN` / `INVALID_TOKEN`.

The two public invite routes (`/invite/verify`, `/invite/accept`) are mounted before `requireOperator`; the route-coverage test allows the `publicRoute` mark only on those two. The global per-IP limiter in `app.ts` also applies. Envelope: `{ success: true, data, meta? }`; errors `{ success: false, error, code }`.

Events emitted by these writes: `ARCHITECTURE.md` (section "Events produced") and the catalogue in `../platform-api/API.md`.

## Provisioning and status changes

**`POST /orgs` in order** (`routes.ts`, Plan 2.5, built; run in Phase 7, 2026-11-17):
1. Plan must exist with `status: 'active'` (404 `PLAN_NOT_FOUND`). An existing slug returns 200 `already_existed`.
2. `seedPermissions()` (global, idempotent) runs before the transaction.
3. In **one transaction**: `Company` (created already `active`), system roles and role permissions (`seedSystemRoles(id, session)`), default security policy (`seedSecurityPolicy(id, session)`), entitlements for every plan product (`source: 'plan'`), first admin `User` (`lifecycle_state: 'invited'`, legacy `role: 'Super Admin'`, pre-set `employee_id`), `UserRole` Super Admin, `Invitation` (`kind: 'first_admin'`, sha256 of a random token, 72 h, made by `lib/invitations.createInvitation`), default access rules (`ACCESS.md`), platform events, operator audit + mirrored tenant `AuditEvent`, and the welcome e-mail row in the outbox (`EmailDelivery`, written with the transaction's session).
4. After commit the sender loop delivers the e-mail (in test/`MOCK_EMAIL` mode an after-commit hook does); its fate is in `EmailDelivery.status`, linked from the response as `invite_delivery_id`. `invite_email_sent: true` means "accepted for delivery".
5. On any failure the transaction rolls back and nothing exists for the slug (no company, roles, policy, e-mail or invitation), so the same request can be sent again. There is no cleanup step and no `provisioning` stub.

**Status changes** (`setOrgStatus`, `routes.ts`): in one transaction set `status`/`is_active`, bump every member's `authz_ver`, mark legacy `RefreshToken`s revoked, revoke live `Session` rows (`revokeSessionsTx`, reason `org_suspended` / `org_closed`), emit the org event, write audit. After commit: tear down provider sessions, then fan out per-member `app_access.changed` in batches of 200.
